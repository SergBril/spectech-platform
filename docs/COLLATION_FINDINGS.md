# Collation mismatch: расследование и вердикт

## Среда

- Образ `timescale/timescaledb`, Alpine 3.23 (musl). Запинен по digest в `docker-compose.yml`.
- `pg_database.datcollversion = '2.41'` (glibc), `datcollate = en_US.utf8`.
- musl не сообщает версию коллации, поэтому `ALTER DATABASE ... REFRESH COLLATION VERSION`
  падает с `invalid collation version change`, а предупреждение печатается на каждом подключении.
- TimescaleDB 2.30.1, гипертаблица `gps_points`, 12 чанков.

Причина расхождения: плавающий тег `latest-pg16` сменил базовый образ с glibc на Alpine
под уже существующим кластером.

## Что измерялось

Пробник **только на чтение** по живой базе: для каждой индексированной text/varchar/name
колонки сравнивался порядок строк, отдаваемый индексом (`enable_seqscan=off`), с порядком
seqscan + явная сортировка под текущим libc. Индексный путь подтверждался через
`EXPLAIN (FORMAT JSON)`; колонки без индексного плана помечались NOT MEASURED.
Транзакция `READ ONLY`, завершалась `ROLLBACK`.

Чувствительность детектора проверена отдельным самотестом: сравнение `ORDER BY name`
против `ORDER BY name DESC` обязано давать расхождение. Результат: `differs=t, first_diff=1`.

## Результат

| Метрика | Значение |
|---|---|
| Всего пар колонка/индекс | 26 |
| Измерено через индекс | 24 |
| Расхождений порядка | **0** |
| NOT MEASURED | 2 (`notification_templates.channel`, `permissions.action` — план Sort) |

**Вердикт: на текущих данных порядок под индексами совпадает с порядком под текущим libc.
Аварийный `REINDEX` не требуется.**

## Отрицательный результат, который нельзя считать доказательством

Пробник на базе, восстановленной из дампа, показал те же нули — но он **невалиден**:
plain-SQL дамп содержит `CREATE INDEX`, поэтому индексы в scratch строятся заново под musl
и не воспроизводят состояние «индекс построен под glibc». Нулевое расхождение там
предопределено конструкцией эксперимента. Измерять нужно живые индексы.

Положительный контроль `COLLATE "C"` против дефолта дал `differs=f` на всех пяти пробах.
Это не поломка методики, а факт о среде: под musl `en_US.utf8` ведёт себя как `C`.
Контроль, сравнивающий тождественные вещи, чувствительность не доказывает — поэтому
и был добавлен самотест детектора.

## Границы применимости

Данных мало: 4 компании, 11 контрагентов, 16 машин, 8 сотрудников. Расхождения
glibc/musl проявляются на смешанном регистре, пунктуации, `ё`/`й`, латинице с диакритикой.
На таком объёме их может не быть просто статистически. «Сейчас не врёт» не равно
«никогда не соврёт».

## Рекомендации

1. Образ запинен — сделано. Это предотвращает повторную смену libc при пересборке.
2. `REINDEX` не делать аварийно. Внести в плановое обслуживание при росте объёма
   текстовых данных или при появлении жалоб на поиск по названиям.
3. Предупреждение о коллации считать косметическим **до** появления наблюдаемых расхождений.
   Повторять пробник после существенного роста данных.
4. Обновление образа TimescaleDB делать осознанно: при смене libc — `REINDEX` в окно обслуживания.

## Побочный урок: как снимать дамп

`pg_dump ... | Out-File -Encoding utf8` в PowerShell **портит данные**: конвейер
декодирует поток консольной codepage и перекодирует обратно, русские строки становятся
mojibake, длины в символах растут, `varchar(20)` переполняется на строке, которая в живой
базе помещается. Один такой дамп дал 1 отбракованную строку и каскад из 8 FK-ошибок.
