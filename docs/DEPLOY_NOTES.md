# Деплой: коммит не означает, что изменение работает

## Что произошло 16.11.2026

Фикс утечки GPS-координат между компаниями был закоммичен в 13:58 UTC, тесты
зелёные, всё запушено. Но процесс backend был запущен в 06:27 UTC — на 7,5 часов
раньше. Python импортирует модули при старте и не перечитывает файлы сам.

Итог: репозиторий содержал исправление, а работающая система продолжала рассылать
координаты техники всем компаниям. Фикс вступил в силу только после рестарта
backend в 15:22 UTC — это подтверждено появлением нового формата строки в логе
планировщика: "Broadcast N positions to 1 companies" вместо старого.

Тесты проверяют код на диске. Они не проверяют память работающего процесса.
Зелёный прогон не является доказательством того, что исправление действует.

## Процедура

| Что изменилось | Что нужно сделать |
|---|---|
| Код backend | docker compose restart backend |
| Код frontend | пересборка образа frontend (статика собирается на этапе build) |
| Зависимости backend | пересборка образа backend |
| docker-compose.yml | docker compose up -d (пересоздаст затронутые сервисы) |
| Только тесты или docs | ничего |

Исходники backend примонтированы с хоста, поэтому файлы в контейнере обновляются
сразу. Но процесс их не подхватывает: uvicorn запущен без --reload (осознанно,
для продакшена).

## Как проверить, что изменение действительно работает

Не по факту коммита, а по наблюдаемому признаку в логах или поведении:

    docker compose restart backend
    docker compose logs backend --since 2m | Select-String "<признак нового кода>"

Признак должен быть таким, которого в старом коде нет: новая строка лога,
новое поле ответа, изменённый формат. Отсутствие ошибок в логе признаком не
является — старый код тоже не пишет ошибок.

## Проверка планировщика

Стартовая строка "Scheduler started ... Jobs: N" раньше показывала 9 из 14:
scheduler.start() и лог стояли в середине функции, а пять задач добавлялись ниже.
Задачи при этом работали (APScheduler допускает add_job после старта), но счётчик
вводил в заблуждение и заставлял искать несуществующую потерю задач.

Теперь старт и отчёт идут после всех регистраций, и в логе видно 14.

## Инвентаризация алертов (17.11.2026)

Проверено исполнением выражений через API Prometheus, а не чтением файлов.

**Что было сломано:** в `prometheus.yml` не было секции `rule_files`. Файл с
правилами был смонтирован и валиден, но не загружался: API отдавал ноль групп.
Десять алертов, написанных ранее, никогда не вычислялись.

**Что работает после починки (12 правил в 3 группах):**

| Правило | Состояние |
|---|---|
| BackendDown | видит данные, up=1 |
| HighLatency | видит данные, p95≈0.10s |
| HighErrorRate | сработает при первом 5xx (серии 5xx пока нет) |
| SchedulerJobFailing / SchedulerJobMissed | сработают при первом провале задачи |
| PostgresDown / ConnectionsNearLimit / Deadlocks | мертвы: нет postgres-exporter |
| RedisDown / RedisMemoryHigh | мертвы: нет redis-exporter |
| DiskSpaceLow | мёртво: нет node-exporter |
| ContainerRestarting | мёртво: нет cadvisor |

**Доставки нет:** секции `alerting` в конфиге нет, Alertmanager не поднят,
`/api/v1/alertmanagers` отдаёт ноль активных. Алерты видны в UI Prometheus и
никуда не отправляются.

**Как проверять, а не угадывать:** пустой результат выражения с сравнением
(`up == 0`) означает «условие ложно», а не «правило сломано». Чтобы отличить
здоровое правило от слепого, надо вычислять основу без сравнения (`up`).
Метка статуса у instrumentator сгруппирована: `status="2xx"`, не `200`.

**Не сделано (требует решения):** Alertmanager с доставкой в MAX через
внутренний webhook backend; экспортёры postgres/redis/cadvisor/node для
семи мёртвых правил.
